# All-mode N+2 integration

September 13, 2026. **Opt-in, bounded real-weight qualification.** This extends
the measured, pure-K5 [cross-step cut](CROSS_STEP.md), not its evidence claims.
Pinned upstreams and installed runtimes remain unchanged.
The nine native scheduler/draft/DSACP/rejection sources used in this reasoning
[byte-match the pins](n2-runtime-source.json) on hw3; this is not a claim about
every installed package file.

## Reuse the queue, complete the contracts

The pinned vLLM `EngineCore.step_with_batch_queue` already submits the next
batch before consuming the oldest receipt. Async V1, PP1 has two concurrent
batches. After retiring N, the host can authorize N+2 while N+1 remains in
flight. We do not introduce another queue or reimplement AsyncScheduler.

- `n2_scheduler.py` subclasses native AsyncScheduler, verifies ordered
  retirement with at most two frames, and enables native deferred KV frees
  even without a KV connector. Cancelled requests cannot donate their blocks
  until the last scheduled device write retires. Reusing a request ID while
  an old frame still names it is rejected; streaming-input sessions are not
  admitted in this prototype.
- `cross_step.py`, explicitly `all_modes=True`, extends conservative CPU
  tiling bounds and late bookkeeping beyond the stable K5 batch. Device
  progress, positions and addresses remain exact. Native input-preparation
  fences remain; pinned H2D sources are not reusable merely because work was
  submitted. The shadow reference rebuilds the original exact metadata.
- Existing target FULL support covers prefill/mixed/decode. `full_draft.py`
  adds bounded context capacity to the DSpark body graph: ordinary K5 and wave-budget banks per request count and execution mode. Context padding is zero hidden,
  position zero, invalid KV slots. Graph cache growth is bounded; an unexpected
  signature change is an error, not an invisible eager fallback.
- Target sampling and metadata preparation are still outside the neural-body
  graphs. FULL here does not mean capturing the CPU scheduler or one graph
  containing an entire server step.

The admitted integration is TP8/PP1, DSV4 DSACP, DSpark K5, at most four seats,
text inputs, no DCP. Extending seat count, other models, structured output,
streaming input and PP requires additional admission/qualification.

## Oracles and first observations

Runs032/033 exposed whole-KV byte differences after context padding, despite
matching draft token IDs. Diagnostic slabs showed positive/negative zero;
padded eager matched padded graph byte-for-byte. That alone does not establish
that every difference is harmless.

`draft_oracle.py` therefore admits **only signed-zero changes in BF16 rows
explicitly addressed by this draft call's context/query slot maps**. All other
bytes in the entire aliased backing still require exact equality. It does not
reinterpret FP32/quantized pages as BF16, permit nonzero tolerance, or alter
live state to make a comparison pass. Reports count the admitted zero words.
The unpadded eager reference is retained. Run034 passed initial capture for
all eight observed count/capacity banks plus 14 replay checks per rank under
this narrower rule, then stopped at a changed metadata signature.

Run035 identified only `num_decodes`, `num_decode_tokens`, and the exact
`num_prefills` count changing within an already-prefill draft body. The pinned
DSACP forward consumes only `num_prefills > 0`; the other counts have no
forward consumer. The private graph view now canonicalizes these fields while
retaining the prefill boolean, attention state, exact tensor offsets and
request-capacity scalar. The reference retains the original metadata. This
avoids graph proliferation across equivalent mixed compositions. Unexpected
changes still stop before any eager fallback.

CPU checks cover two-wave FIFO retirement including empty frames, request-ID
reuse after cancellation, the actual pinned native deferred-free methods,
padding/reference restoration, and the zero exception's address boundary.
`turnover.py` adds requests during live decode, aborts one, and checks final
output lengths, stale-output suppression and drain using the native engine.

## Reproduction

Use the existing lease/admission launcher with a fresh capsule and:

```
--tp 8 --spec --mode FULL --budget 288 --n2 --ordered-replay --cpu-qli --turnover
```

For shadow, set `FULL_MIXED_SHADOW=1`, `DRAFT_GRAPH_SHADOW=1`, and
`HCCL_DETERMINISTIC=strict`. Shadow timings and memory are not performance
measurements. Use a separate ordinary-HCCL run for performance and profiling.
The launcher snapshots every Python source file into the capsule.

## Qualified dummy envelope

[Compact all-rank receipt](n2-shadow.json), run036: seven heterogeneous cohorts
plus online turnover/cancellation completed. Every rank passed 96 target checks
(13 prefill, 11 mixed, 72 decode), all target output/KV/MTP differences zero.
The draft passed eight first-capture checks and 45 later replay checks/rank;
only addressed signed-zero equivalence was needed, with no eager fallback.
There were 83 exact-metadata shadow checks and 78 late callbacks/rank.

The scheduler issued/retired 114 frames, reached two in flight, retired all 99
positive device waves, and ended with no pending frames or deferred frees.
The online workload completed the intended 64/16/16 output lengths after an
abort; no cancelled output escaped. This does not replace an audit of page
ownership under memory-pressure preemption or unbounded request concurrency.

All reported shadow timing/memory includes the oracle and is not a serving
result. Real-weight qualification below uses the explicit padded-program oracle.

## Real-weight padding boundary: not original-donor bitwise equivalence

Run037 rejected a mixed draft call: 2/10 proposal IDs differed from unpadded
eager. Run038's [controlled diagnostic](n2-padding-diagnostic.json) isolated
the cause on all eight ranks. For 146 real context rows padded to 288:

- Padded eager and graph have identical proposal IDs and **all KV pool bytes**.
- Repeating unpadded eager reproduces its original IDs. Restoring the original
  logging counts also leaves its IDs unchanged; metadata canonicalization is
  not the cause.
- The first draft cache has only 3 differing BF16 values (maximum .00390625).
  The difference amplifies downstream: later draft caches differ by as much
  as .818359375. This is not merely signed zero and must not be labeled such.

The full-bank implementation is therefore a **padded proposal program**, not
a bitwise reproduction of the original unpadded draft. Its graph-equivalence
oracle is explicitly selected with `FULL_DRAFT_REFERENCE=padded`; this requires
exact IDs and whole-KV bytes, with no signed-zero exception. The default remains
`unpadded` for diagnostic comparison and preserves the original failing gate.

In this greedy-only harness, the unchanged Ascend rejection kernel publishes
target argmax IDs and stops at the first mismatch; it never trusts an arbitrary
wrong proposal. A hardware fixture exercises the actual K5 Triton rejection
kernel. Target output/state and exact-progress oracles remain unchanged. This
separates target correctness from draft proposal quality: padding can change
acceptance and work counts, which must be included in the performance result.
It is not evidence about stochastic sampling, model quality benchmarks, or
equivalence to an unpadded draft's proposal distribution.

## Qualified real-weight envelope

Both runs use TP8, full real DSV4-Flash weights, K5, strict HCCL, four seats and
3 GiB KV/rank to leave shadow headroom. Seven heterogeneous cohorts plus online
request insertion/cancellation complete. All eight ranks agree on these counts:

| Run / global budget | Target checks (prefill / mixed / decode) | Draft first / later checks | Exact-metadata checks |
| --- | --- | --- | --- |
| 039 / 288 | 74 (13 / 8 / 53) | 8 / 42 | 61 |
| 040 / 4128 | 67 (9 / 6 / 52) | 8 / 38 | 58 |

Target output, MTP and whole-KV comparisons are zero-difference. Draft graph
matches the **padded** eager program in IDs and all KV bytes, with no signed-zero
exception. Every positive target wave is asserted FULL (74/67 per rank), and
no draft fallback occurs. The actual Ascend K5 rejection-kernel fixture passes
on all ranks; target verification is unchanged.

Both runs actually defer 18 request frees, reaching three queued deferred-free
entries, then drain completely. Run040 issues/retires 78 scheduler frames and
all 67 positive device waves. The inserted requests finish at their intended
lengths and the cancelled request emits no later output. This establishes the
bounded request-lifecycle path, not a memory-pressure preemption stress test.

Performance comparison against the preceding stable-K5-only cross-step path is
collected separately with ordinary HCCL and both shadows disabled. It is not
a comparison against an untouched donor, nor an accuracy claim about the
original unpadded proposal stream.
