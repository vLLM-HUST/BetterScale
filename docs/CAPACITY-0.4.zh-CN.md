# 自动 KV 定容与上下文容量

BetterScale 0.4 的变化不是把90%换成另一个百分比，也不是强制分配更多KV。
不传 `--kv-cache-memory-bytes` 时，它先完整测量执行程序的驻留成本，再把实际
可用余量交给原生缓存管理器；固定字节仍保留为用户明确选择的手工路径。

## 四个数字不要混用

| 指标 | 意义 |
|---|---|
| 物理KV字节/rank | 该rank真实获得的缓存预算 |
| `max-model-len=524288` | 单请求输入加输出的上限，不是承诺的并发量 |
| TP四席位、DP每rank两席位 | 活跃请求数上限，长请求仍可能因容量排队 |
| 原生日志的KV tokens | 按当前horizon计算的混合缓存等效量，不是固定token槽数 |

SWA确实有滑窗回收；大prefill波次会提高滑窗和compressor峰值，不能把窗口长度
单独当作全部驻留状态。C4与C128共享原生分配约束，有对齐/padding税。
原生当前物理block32，对应APC公共对齐4K，不能沿用旧脚本block128得到16K的结论。
**本次没有开启APC**，也没有改变原生KV布局、哈希协议或TP复制关系。

LiveInfer的8GiB约500K是历史近似印象，不是本次等配置基线。本报告不把mapped
主存容量、HBM容量、全局请求数和原生等效token数混在一起比较。

## 已取得的证据

- **TP真权重（run190）：** 同一target/draft graph池，自动KV14.939–14.948GiB/rank，
  READY后约0.965–0.974GiB/rank空闲；32题原始LongBench检索全对，另完成60K输入与
  八个8K输入的周转。不是全套OpenCompass，也不是新的原生baseline吞吐比较。
- **TP dummy容量（run188/189）：** 完成单448Ki输入和四个128Ki输入；四个448Ki输入、
  各生成2048token的压力队列完成，最高KV占用96.84%，最多三个长请求同时运行，
  第四个排队；随后16个8K请求也完成。运行期额外分配峰值约326MiB/rank。
  这证明该形状的容量与回收，不是真权重吞吐或长上下文语义质量。
- **DP真权重（run170/171/174）：** 自动KV约7.9GiB/rank，32题检索全对；八个60K输入
  完成；另一个512K配置下单448Ki输入完成。随后更重队列达到外层时间上限，
  不能宣称DP长历史满池/服务质量验收通过，也不能把超时说成OOM。

精确记录在`evidence/auto-kv-run{170,171,174,188,189,190}.json`。
每条证据保留真实代码和负载身份；打包集成验证单独记录。

## 开销与边界

启动阶段多做一次小State试捕获，得到完整graph成本；target/draft使用**同一个
graph池**。旧graph句柄留存以维持已观察到的通信资源生命周期，旧State与元数据
退休且永不再replay，不能用第二个完整arena绕开这个问题。

保留1GiB/rank安全量及eager/non-Torch预算。空间用满指合理利用剩余容量，
不是把驱动空闲压到零。并发进程在定容后占卡不在本算法的仲裁能力内。

此前3GiB诊断预算下的抢占恢复失败仍是已知边界；96.84%压力没有发生抢占，
所以没有“靠大预算证明抢占已修好”。席位数、graph桶及模型/pins仍受明确准入约束。
