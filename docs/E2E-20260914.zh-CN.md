# BetterScale：保留优化对原生 donor 的端到端验收

2026-09-14，hw3，8×Ascend 910B2，DeepSeek V4 Flash W8A8，K5。

这次比较的是**原生 donor 与已有优化组合**，不是“提前预算”增量补丁。
TP 观察到明确的 prefill / 请求轮换吞吐改善；DP 的成绩区分旧0.3.0与
现已收进0.3.1的预热实现。不能把后者的收益标成0.3.0的收益。

不是新wheel重跑的数字。TP执行路径未改，沿用161的 **+35.17%**。

本轮核对了producer、metadata、warmup、host/packet、target_full和cross_step等
DP代码与155所用`81ecde3`一致，worker的DP安装分支一致；保留DP-only准入，

## 原始测量程序与比较边界

- **发布版**：`vllm-betterscale==0.3.0` 的源码快照；main `7f0bbdb` 的 `src/`
  与 release tag `v0.3.0` 无差异。本轮通过其原生 Worker 入口跑 HTTP，
  不是重新执行一次 wheel 安装验收。
- **原生 DP**：直接使用 donor `NPUWorker`，无 BetterScale 性能补丁。
- **原生 TP**：只加 K5/TP8 必需的 `compat_lcm` 启动修复；不含 FULL prefill、
  draft、metadata、ordered replay 等性能补丁。因此它是“原生执行 + LCM 兼容修复”，
  不是完全零修改的发行包。
- **DP 预热版**：复用本次同机已完成的155，既有优化在 READY 前准备 producer /
  metadata banks；没有提前预算 executor。其22个运行时 Python/JSON 文件直接比较
  与 `81ecde3` 实验分支一致。该程序尚未进入0.3.0。
- 155名称中的 `control` 只是它在上一轮**增量实验**中的身份，不代表原生 donor。
  本报告按实际程序重新标注；不纳入156的提前预算候选。

固定运行环境为 vLLM0.25.1、vLLM-Ascend0.25.1rc1、torch-npu2.10.0.post2、
CANN9.0.1，同一现有 donor 环境与模型；没有换 pin、重新调优 donor 或更换权重。
所有组使用 native MP executor、async scheduling、原生共享专家 overlap、标准 rejection，
prefix cache 关闭。没有 profiler、shadow oracle 或每波 JSONL 收据写入。

## 负载与计时

每个程序先执行相同的短 HTTP 前导组（128输入/32输出），单独记录其成本。
随后以下三类负载各执行三轮，保留所有轮次，不删除较慢的首轮：

- occupied decode：C个请求，每个128输入、256输出；
- balanced prefill：C个请求，每个4096输入、128输出；
- skew/turnover：2C个排队请求，一个8192输入，其余256输入，每个128输出。

DP的C=16，TP的C=4。这是固定输入/输出长度的合成 HTTP 服务负载，不是
SWE/Terminal Bench/OSWorld 原始 agent 轨迹。生成 token、draft acceptance 和原生
调度不被强制相同；逐轮计数保留在[CSV](evidence/retained-e2e-20260914.csv)。

加载、初始化、前导组、质量验收不计入下面九组计时。**READY 后仍可能发生的
首次 shape/capture 成本没有删除**。同一进程内三轮，不是三次独立启动的统计重复。
各程序依次执行，未随机化顺序；预热版155早于本轮158–161，其复用身份明确保留。
所有成功组的 NPU 监控无占用冲突，原生 preemption 计数为0。

## 结论与未跨过的边界

1. **TP发布版**：合计输出吞吐+35.17%；prefill和轮换负载的三轮吞吐都高于对应
   原生轮次。但decode的chunk-gap P99变差，不能声称所有延迟指标都改善。
2. **DP发布版**：合计吞吐−6.11%，首轮三类负载均明显偏慢。源码仍有首次遇到
   shape时的辅助graph构建；这与已验收的启动预热版不同。这里没有新timeline来把
   每个慢点完全归因，不能仅凭首轮变慢断言所有差异都由capture造成。
3. **DP预热版**：合计吞吐+39.63%，三个负载吞吐中位数和TTFT P95中位数都优于
   原生。decode吞吐并非每轮都赢；这是同机有限样本的既有成绩，不是任意流量的保证。
4. 五个程序均完成保留的32道原始长上下文检索题，按未修改的 pinned OpenCompass
   evaluator `60a28a7` 得到32/32。不是完整OpenCompass套件、全模型精度认证或
   新一轮全KV逐字节shadow检验。
5. 原始测量不推导最大服务并发、任意SLO容量或长期agent吞吐。本轮不启用、不推广
   没有稳定增量收益的 early-budget executor。测量之后的0.3.1集成见上方发布归档。
